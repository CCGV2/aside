# ADR 0001：互动播客的架构与实时问答设计

> 历史设计记录。后续已改为按需 Live、回答后静默自动续播，并移除手动「插一句」按钮；下文的目录拆分是初始规划。当前实现见[架构说明](../architecture.md)与 [ADR 0002](0002-on-demand-live-sessions.md)。

- 日期：2026-09-10
- 状态：已接受的设计方向；接口与体验参数待原型验证
- 技术栈：TypeScript，浏览器 Web App，Node.js 后端

## 背景与目标

用户导入播客音频，在听原声时可以直接开口打断。应用暂停节目，由 GPT-Live 延续主持人的表达口吻回答问题，支持连续追问、再次打断和调用知识检索工具。用户明确表示继续后，节目从一个自然的语义起点恢复。

首版在本地运行，保留未来前后端分开部署、分析任务独立扩容和存储迁移的能力。本 ADR 记录设计决定，不代表已完成接口接入或实际音频效果验证。

## 已确定的产品行为

1. 上传本地音频，整期分析完成后进入互动播放。
2. 播放原音频，问答使用 AI 预设声音，并参考主持人的用词、解释习惯和表达风格。
3. 自动分析说话人的声音倾向：全部偏男声则选男声，全部偏女声则选女声；混合时按累计说话时长决定。平局或不明确时跟随主讲人，仍不明确时使用固定默认声音。该分类用于声音选择，不认定人物性别。
4. 不让用户选择音色，整期收听保持固定。多人播客首版统一使用选定声音；回答参考提问对应说话人的表达风格，避免混淆不同人的观点。
5. 回答语言跟随用户当前提问。短句无法判断时沿用上一轮语言；首次无法判断时等待进一步输入或沿用界面语言。引用外语词语不自动触发语言切换。
6. 支持多轮问答。沉默不视为结束；用户说“继续”“没有问题了”等明确结束意图后才能恢复。“懂了”等模糊表达可简短确认。
7. 保留“提问”和“继续播放”按钮作为辅助入口，直接开口打断仍是核心功能。
8. 默认避免透露未听内容，区分节目已有观点、AI 推断和外部补充资料。

## 决策：engine / backend / frontend 三大块

```text
aside/
├── engine/src/
│   ├── domain/          # 节目、内容地图、插话与会话模型
│   ├── analysis/        # 音频分析流程
│   ├── resume/          # 恢复点生成和选择
│   ├── context/         # 上下文组装与检索规则
│   ├── conversation/    # 问答编排、任务版本、语言与结束意图
│   ├── playback/        # 不依赖浏览器的播放状态机
│   └── ports/           # 转录、模型、检索、持久化等接口
├── backend/src/
│   ├── api/             # HTTP、进度和应用事件接口
│   ├── jobs/            # 分析任务调度、重试、恢复
│   ├── sessions/        # 会话建立与恢复
│   ├── adapters/        # OpenAI、FFmpeg、数据库和文件存储
│   └── contracts/       # API 格式及运行时校验
├── frontend/src/
│   ├── pages/           # 节目页、互动播放器
│   ├── components/
│   ├── audio/           # 麦克风、原音频与 AI 输出
│   ├── live/            # GPT-Live 浏览器连接适配
│   ├── controller/      # 执行状态机动作并回报结果
│   └── api/             # 后端客户端
└── .docs/adr/
```

### engine

engine 是库，初期不是独立服务。它包含领域规则和流程，通过接口调用外部能力，不直接依赖 HTTP 框架、数据库实现、供应商 SDK 或浏览器 API。

- `engine/core`：浏览器安全的数据模型、播放状态机、恢复点选择。
- `engine/server`：分析流程、上下文与问答编排，由后端调用。

用包导出和依赖检查阻止前端导入服务端入口。backend 提供端口实现，例如转录模型、文件读取和检索服务。未来需要独立扩容时，再将相关 engine 能力包装成服务。

### backend

负责上传、音频访问、数据持久化、分析任务、Live 会话创建、知识工具执行和模型接入。密钥仅保存在服务端。分析任务独立于 HTTP 请求生命周期运行。

API 合约独立于路由实现；frontend 仅依赖合约或生成的客户端，不导入 backend 运行时代码。

### frontend

frontend 就是首版实际使用和测试的 Web App。它负责麦克风采集、原音频和 AI 音频播放，以及实际播放位置。浏览器通过 WebRTC 连接 GPT-Live，后端处理会话建立与委派业务。

浏览器中的 PlaybackCoordinator 使用 engine/core 状态机。后端发出动作建议，由前端校验并执行；实际播放状态以浏览器为准，后端保存检查点。暂停不等待网络往返。

## 音频分析与内容地图

保留完整原音频，分段以时间坐标记录，不要求切割成很多媒体文件。时间统一采用原音频毫秒坐标，倍速不改变坐标含义。

```text
音频校验与元信息
  → 转录、词语时间对齐、说话人区分
  → 句子/分句与语义段落
  → 候选恢复点及音频落点修正
  → 主题摘要、术语和原文索引、主持人表达特点
  → 自动选择预设音色
  → 可互动播放
```

每阶段持久化输入版本、输出和状态。重试从失败阶段继续；更换转录或分析版本会使依赖它的下游结果失效。保存转录与边界置信度，低置信度时采用保守恢复点，并允许在开发面板检查。

导入时准备节目内部知识，不预先生成全部潜在问答。外部资料与复杂背景解释按需查询，结果可缓存。字幕和说话人判断需通过样本验证，不把模型输出视为精确事实。

## 核心数据

| 对象 | 内容 |
| --- | --- |
| Episode | 原音频、时长、处理状态 |
| EpisodeAnalysis | 转录、说话人、段落、摘要、音色决定、分析版本 |
| ResumeAnchor | 自然恢复位置、对应文本、语义范围与置信度 |
| ListeningSession | 播放进度、固定音色、回答语言、会话检查点 |
| Interruption | 实际打断点、恢复点、关联问答与分析版本 |
| ConversationTurn | 用户发言、AI 输出、来源、播放与打断状态 |
| KnowledgeTask | 工具任务、问题版本、执行状态和结果来源 |

```ts
type Interruption = {
  id: string;
  sessionId: string;
  analysisVersion: string;
  interruptedAtMs: number;
  resumeAtMs: number;
  anchorId: string;
};

type ResumeAnchor = {
  id: string;
  startMs: number;
  endMs: number;
  kind: "sentence" | "clause" | "topic";
  text: string;
  confidence: number;
};

type KnowledgeTask = {
  id: string;
  interruptionId: string;
  questionRevision: number;
  tool: "get_passage" | "search_podcast" | "search_web";
  state: "idle" | "running" | "completed" | "failed" | "superseded";
};
```

节目分析可被多次收听复用，进度和问答属于收听会话。恢复已有插话时使用其记录的分析版本，避免重分析后恢复点悄然变化。

## 打断与自然恢复

示例原音频：“今天天气真好，我们〔打断〕准备出去走走。”

- 精确记录“我们”之后的实际打断位置。
- 恢复点选择“今天天气真好”开头，而非简单回退固定秒数。
- 优先选择完整语义句；长句允许选择完整分句，再根据词语对齐和停顿微调到第一个字之前。
- 同一次插话内，打断 AI、连续追问都沿用原恢复点。
- 回退范围及长句阈值通过试听确定；运行时使用预计算的候选点，不临时调用模型决定。

播放状态流：

```text
播放 → 用户开口 → 立即暂停并记录位置 → 听取问题
     → 回答 ↔ 追问 → 等待用户明确结束
     → 校验恢复条件 → 从自然起点播放
```

必须满足以下规则：

1. 原音频和 AI 正式回答不同时播放。
2. 用户打断 AI 时立即停止其声音。停止生成、清理缓冲和同步已听位置由供应商适配层按真实协议实现并验证。
3. 模型生成完成不等于音频播放完成，恢复以实际输出完成信号为依据。
4. 恢复前检查用户明确结束意图、无新发言、AI 输出结束以及命令版本仍有效。
5. 用户恢复前又开口，撤销待执行恢复动作。
6. 问答期间手动拖动进度条，视为选择新位置，旧自动恢复计划失效。
7. 断线保持暂停；重连保留进度，禁止重播旧回答或执行旧恢复命令。
8. 同时记录节目进度、问答版本和连接代次，丢弃过期事件。重建 Live 会话可恢复业务上下文，不宣称复原供应商内部状态。

## GPT-Live 与多轮工具问答

使用 `gpt-live-1` 负责实时语音交流，采用 client delegation 让 engine/backend 控制上下文、工具执行和结果回传。语音模型与后端推理模型分别配置，后端模型选型待实际质量和延迟验证。

工具的领域接口：

| 工具 | 作用 |
| --- | --- |
| get_passage | 获取指定时间附近的节目原文 |
| search_podcast | 检索整期段落、概念及其出处 |
| search_web | 查节目外部或时效性资料 |

这些是计划提供给后端问答代理的工具，不假设 GPT-Live 的原始协议直接使用这些函数格式。Live 委派、工具调用和结果回传由适配层转换。

播放器持续准备当前位置附近的上下文；真正发问时冻结一个快照：当前句子、最近约 60–120 秒原文、已听摘要、历史追问、主持人风格和回答语言。按需追加检索结果，不每轮发送整期全文。

材料附带时间戳或来源链接，并标记已听/未听范围。节目内容作为资料而非系统指令。涉及外部事实时保留来源；用户明确要求提前解释后面的内容时才放宽默认防剧透策略。

应用内部事件与供应商事件分离，例如 `user_speech_started`、`assistant_audio_finished`、`resume_requested`、`connection_lost`。这些名称为应用自定义，不是对 GPT-Live API 事件名称的断言。

## 查询空档与延迟

语音状态与知识任务状态正交：AI 可以讲话，同时后台查询运行。用户打断声音不自动取消任务；问题改变时更新问题版本，取消可取消任务，或将结果标记过期。

- 当前上下文足够时直接回答，避免多余检索。
- 短查询安静等待；明显变长时简短说明具体查询动作。
- 约一秒后考虑进展提示，仅作为原型参数，不是性能承诺。
- 有可靠部分结果时先回答确定内容，不用推测填补等待。
- 用户可以在等待中补充问题，后端据此调整任务。
- 查询超时或失败时清楚说明局限，不反复填充语或无限重试。
- 用户恢复播客后，迟到结果只保存记录，不突然播放。

本地检索、上下文预准备与缓存优先于口头填充。外部检索设置执行时限和有界重试，具体数值通过测量确定。

分别测量：开口到暂停、问题结束到首次有用回答、工具耗时、输出结束到恢复、误打断率、恢复点自然度。填充语不计为首次有用回答。

## 本地运行与部署演进

初期统一命令启动 Web App、API 和分析任务进程。本地目录保存音频，本地数据库保存元信息、任务和会话；具体数据库选型实现时确定。数据持久化以支持刷新、重启及失败恢复。

未来 frontend 独立托管，backend 与分析任务分开扩容，本地文件适配器替换为对象存储，数据库按并发需求迁移。engine 保持库形态，不提前引入微服务或分布式消息系统。

首版优先保持 Live 会话连接验证随时插话；会话按时长计费，后台模型和工具另外计费。必须显式结束闲置会话并记录用量。按需连接会增加首问延迟，作为后续对比方案。

## Web App 与验证

两个页面：节目页提供上传和分析进度；互动播放器提供原声播放、字幕、麦克风状态、问答记录和辅助按钮。主要以桌面浏览器和耳机验证；外放回声导致误打断是独立待测项。

开发调试面板展示状态转换、精确打断点、恢复点试听、发送给模型的上下文、任务版本、连接错误及关键耗时。不得记录密钥。麦克风状态须清楚可见。

模拟模式与真实模式复用同一个状态机和播放器。模拟模式使用固定分析结果和语音事件验证规则；真实模式连接麦克风和 GPT-Live 验证完整体验。

必要自动验证：句中恢复、连续追问保持恢复点、旧任务与命令失效、沉默不恢复、恢复前再次发言、手动拖动覆盖恢复点、断线不丢进度、分析任务重试不重复已完成工作。

实际试听验证：中英文提问、说话人混合、长短句恢复、AI 被打断、后台查询期间补充问题、音色倾向选择以及耳机/外放表现。测试通过不等于听感验收。

## 实施顺序

1. 建立三模块依赖边界、核心模型和 Web App 骨架。
2. 实现上传、持久化任务、分析进度和原声播放器。
3. 用固定内容地图验证播放状态机与自然恢复。
4. 接入真实转录、内容分析和自动音色选择。
5. 接入 GPT-Live 多轮语音与 client delegation。
6. 接入节目知识检索和外部搜索，验证延迟与过期任务处理。
7. 完成实际试听、断线恢复和用量检查。

## 未决实现细节

- GPT-Live 当前 SDK、client delegation 协议、取消输出及播放完成信号需按官方文档和真实会话验证。
- 转录、说话人区分、词级对齐及声音倾向分析的供应商与模型待样本评估。
- 男声/女声预设的具体 voice ID 需核实可用音色并试听。
- 语音检测、回声消除、恢复点阈值与等待提示阈值需测量后确定。
- 后端模型、数据库与本地检索实现尚未锁定，不影响已确定的领域边界。
